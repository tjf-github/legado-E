# 语料逐条归因

把用户于 2026-09-22 交付的 [`语料/2026-09-22-AI正文异常样本库V1.md`](语料/2026-09-22-AI正文异常样本库V1.md)
的 **59 个样例**，逐条判定「这个输入形态最可能是**哪一层**产生的」，并标出可复现性。

> 用户的交付说明是「**只看样例，不看规则**」——本文件只用每条的「输入 / 预期」文本，
> 不采用语料自带的决策表（`FIX`/`KEEP`/…）与验收规则（那是 AI 后处理层的规格，§14.2 本批不碰）。

## 一、怎么产生的，以及怎么读这张表

11 个分类各由一个 agent 读语料 + 读 Kotlin 源码给出初判，
每一个非「AI层 / 无法判定」的初判再交给**一个独立的对抗验证者**，
要求它默认立场是「这个判定站不住」，亲自打开文件、顺着调用链走一遍才允许判「成立」。

**结果：46 条送验，34 条被推翻。** 这个比例本身就是最重要的结论，见第四节。

### 两条必须分开的语义

「层」这个词在初判里被用成了两种意思，本文件统一如下：

| 列 | 含义 |
| --- | --- |
| **产生层** | 这段文本**从哪来**。取值：`站点原有文本`（原站 HTML 里就是这样，解析层只是照搬）/ `书源层`（某条书源规则写的）/ `通用解析层`（`HtmlFormatter`、`ContentProcessor`、`AnalyzeRule` 等与书源无关的代码）/ `展示层`（`TextChapterLayout`、`ReadBook`）/ `AI层`（§14.2 冻结分支）/ `无法判定` |
| **责任层** | 该由谁处理。**KEEP 类样例（A05、C05、E05、F05、G05、H01—H05、I03、J05、J06）问的不是「从哪来」而是「谁可能改坏它」**，本文件在表里用「→ 责任层」单列 |

**不区分这两者会直接误导下游**：初判里 A05（合法花括号，KEEP）判「站点原有文本」，
H03（代码里的花括号，KEEP）判「通用解析层」——同一种东西拿到两个层，
而看到「通用解析层」的人会以为有东西要改。

### 口径警告

本文件涉及「全库多少」的地方，一律注明是**单份清单 S**（zip 内 `bookSource.json` 一份）
还是 **`--merge-collections` 归并 M**（zip 内 16 份合集按 `bookSourceUrl` 归并）。
两者差别很大：`has_title_rule` 在 S 下是 0、在 M 下是 36；启用数 4000 vs 4417。
**不写口径的数字没有意义**——这条已经被一次实际误判踩中（第四节）。

## 四、我采纳的结论

### 4.1 最重要的一条：语料是**手写样本**，不是可回溯的现场证据

34/46 被推翻，压垮判定的是同一个理由：**语料只给了「AI 实际收到的文本」这一行字**
（语料自己的字段定义在 §3 模板：`input: AI 实际收到的文本`），
既没有原始 HTML、没有书源标识、没有链路日志。

这带来一个直接后果：

- 对 **A 类（字符污染）**，判定「站点原文」还是「书源替换段」还是「通用层写入」，
  靠排除法都站不稳——而排除法只要漏掉一条通用层写入路径就会翻车（下面就翻了）。
- 因此 A 类**不满足 §7 的退出条件**：它既不能离线复现到「某条真实链路」，
  也不能标记为「仅真实站点可复现」（因为连「真实站点上确实发生了」都没证据）。
- **B01 是例外**：语料给了原始 HTML（`<p>他走到山门前。</p><p>守门弟子拦住了他。</p><p>他取出令牌。</p>`），
  所以「解析层丢了一段」这件事**可以离线复现**。

结论：**A 类改判为「样本不可回溯，需真实链路四段快照」**；B 类部分可用。

### 4.2 通用层确实有写入正文的路径，而且不止一条

反驳者们在推翻「站点原有文本」时，各自找到了通用层**主动写入正文**的路径：

| 路径 | 位置 | 后果 |
| --- | --- | --- |
| 替换净化抛 `RegexTimeoutException` 时把异常栈写进正文 | `ContentProcessor.kt:185`（`item.name + e.stackTraceStr`） | 正文里出现规则名与堆栈 |
| `<usehtml>` 占位串被替换规则命中 | `ContentProcessor.kt:151-154` 写入字面量 `特殊格式的占位不应该被看见N。`，`:193-194` 才还原，而替换净化在 `:157-192` **之间**跑 | 这句中文永久留在正文 |
| `&#10;`/`&#160;` 等实体躲过格式化、解码后才成真 | `BookContent.kt:244-247` | 多余空行 / NBSP —— 已立为 [诊断卡 07](诊断卡/07-实体解码与格式化次序.md) |
| `{{}}` 求值产生 NaN 时原样打出字面量 | `AnalyzeRule.kt:742-747`（`is Double if jsEval % 1.0 == 0.0` 对 NaN 恒假 → `toString()`） | 正文里出现 `NaN` |

**这四条在本次归因之前一条都没被登记。** 它们是本文件最实的产出。

### 4.3 判定被推翻的典型形态

1. **排除法站不住**：初判用「通用层不会碰它 ⇒ 那就是站点原文」下结论，
   而枚举漏了展示层与 `ContentProcessor` 的替换净化整支。
2. **口径混用**：同一条分析里混了单份清单与归并口径的数字（`has_title_rule` 0 / 36）。
3. **把「可能碰它」当成「它产生的」**：H01—H05 全判「通用解析层」，
   但用 `HtmlFormatter` 的 9 条正则重放后内容一字不改 —— 那是推测，不是验证。
4. **行号没核**：多条初判引的行号对不上被引代码的内容。

### 4.4 对 `ruleContent.title` 的一处实际误判（口径）

「正文出现标题」专项的一个角度拿着**单份清单**（S）的报告下了「全库 6139 条**没有一条**用
`ruleContent.title`，所以问题 100% 落在通用层」的结论。
另一个角度给出 M 口径 **36（启用 26）**。复跑确认 **M 口径正确**。
这条错误的「100%」会直接导致「只改通用层」的实施决定 —— 已记入 [诊断卡 06](诊断卡/06-正文出现标题.md)。

### 4.5 补判 D02—D05

| id | 产生层 | 责任层 | 依据 |
| --- | --- | --- | --- |
| `D02` 域名推广 `最新网址：www.example.com` | 站点原有文本 | 书源层（`replaceRegex`） | 通用层没有任何依据能判断「哪一行是推广」；快照里大量源正是用 `最新网址.*` 这类交替分支在删它 |
| `D03` 导航文字 `上一章 目录 下一章` | 站点原有文本 | 书源层 | 同上；注意**导航行与标题行是两件事**，删导航不能连标题一起删（语料 D03 预期保留标题） |
| `D04` 作者的话 | 站点原有文本 | **不删**（语料决策 `UNCERTAIN`） | 作者附言不一定属于垃圾内容，默认保留并标记 |
| `D05` 登录提示 `请登录后继续阅读` | 站点原有文本 | 书源层 | 站点 UI 文本，规则层删 |

四条的共同点：**「该删的没删」不是通用层的缺陷**，通用层无从知道该删什么。
它们属于 `诊断卡/PENDING.md` §2「多出符号 / 跳行」三种成因里的第二种。
