## 3. 三条检查的读数

判定对象一律是 `replaceRegex` 按 `##` 切分后的**匹配段**（`makeUpRule` 的
`ruleStrS[1]`）。写成 JS 的 `replaceRegex`（54 条，启用 26）整串交给 JS 求值、
不走 `##` 分段，已排除在判定之外。

### 3.1 匹配段以未转义的 `|` 结尾 —— `replace_regex_trailing_pipe`

| 项 | 值 |
| --- | --- |
| 计数（全部 / 启用） | **43 / 30** |
| 判定口径 | 去掉转义的 `\|` 之后，匹配段以 `\|` 结尾 ⇒ 末位分支为空 |
| 代表 `url_hash` | `013235e9c256`、`068d039991f2`、`0957169fcb06`、`1a648d1b9f31`、`1c80380be1c3`、`2027a2fe8868` |

空分支在多数正则实现里是**合法**的（匹配空串），后果是命中位置不确定。
是否真的出问题要看替换内容——若 replacement 为空串，空匹配在部分实现下会导致
替换行为退化。**属候选，不是已定论的问题。**

### 3.2 匹配段含未转义的 `||` —— `replace_regex_empty_alternative`

| 项 | 值 |
| --- | --- |
| 计数（全部 / 启用） | **3 / 3** |
| 全部 3 条 `url_hash` | `80cb2446e1b5`、`a3f18b9051cb`、`edd0bd19188d` |

**3 条全部列出**，这是本次最容易逐条核完的一组。3 条也都启用。

### 3.3 匹配段含嵌套量词 —— `replace_regex_catastrophic_backtracking`

| 项 | 值 |
| --- | --- |
| 计数（全部 / 启用） | **8 / 5** |
| 判定口径 | 匹配段含 `(...[+*]...)[+*]` 形态，如 `(.*)+` |
| 代表 `url_hash` | `4745dc5add4f`、`75d4660da8d8`、`91e6e7a355fb`、`99940d8a7c3f`、`aaa39f0dc356`、`cf104daf4ab6` |

这是三条里**唯一有明确后果**的一条：嵌套量词在长正文上可能触发灾难性回溯。
§6 B0 把「替换超时」列为独立的错误类别，`ContentProcessor` 里也有
`RegexTimeoutException` 的处理分支（捕获后会**停用该条替换规则**）——

```kotlin
} catch (e: RegexTimeoutException) {
    item.isEnabled = false
    appDb.replaceRuleDao.update(item)
    mContent = item.name + e.stackTraceStr
```

注意这里 `mContent` 被赋成了 `item.name + 错误堆栈`，也就是**把错误文本写进了正文**。
这属于通用层行为，不在本卡范围，但它是「替换超时」这个错误类别的真实后果，P1 时应一并观察。

### 3.4 零命中的一条：`replace_regex_unparsable`

| 项 | 值 |
| --- | --- |
| 计数（全部 / 启用） | **0 / 0** |

判定口径：`replaceRegex` **既不是 JS/WebJS 规则、又不含 `##` 段**——此时
`makeUpRule` 只会得到一个非空的选择器，`replaceRegex` 保持默认空串，替换逻辑整个不生效。

零命中说明**现有 1635 条 `replaceRegex` 全部可用**：要么是 `##` 分段式，要么是 JS 式。
这条检查列在报告里是为了确认口径生效，不是报问题。

### 3.5 顺带记录：JS 式 `replaceRegex`

| 项 | 值 |
| --- | --- |
| 计数（全部 / 启用） | **54 / 26** |

对应旗标 `has_js_replace_regex`。这类值整串交给 JS 求值，**任何基于 `##` 切分的
静态判定都会误伤**——本次实现中一度把它算进了「缺 replacement 段」（36 条）与正则结构
检查里，全部是误报，已修正。工具的 README 里写明了这一点，避免将来被改回去。
