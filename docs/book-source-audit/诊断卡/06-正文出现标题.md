# 诊断卡 06 · 正文里出现章节标题

> 用户于 2026-09-22 追问的一类：**「还有一类是正文出现标题，不知道考虑到没有」**。
> 结论：**之前没有考虑到**——它不在 `INVARIANTS.md`、不在当时的 8 个冻结用例、不在这五张卡里。
> 本卡是补上的，并同时补了 `bookSourceBaseline/case-09-title-in-body/` 与
> `tools/book-source-audit/` 里的三条检查 + 两个旗标。诊断卡模板见 `TEMPLATE.md`；
> 本卡是**问题类卡**（同 05），不绑定单个书源。

## 1. 现象

阅读时同一章标题出现两次以上。渲染路径上一共有**三个**来源，任两个同时出现就会看出重复：

| 来源 | 代码 |
| --- | --- |
| 布局标题（正文流的一部分） | `TextChapterLayout.kt:225-325`，`displayTitle` ← `TextChapter.getDisplayTitle()` |
| 页脚 tip（默认开） | `ReadBookConfig.kt:588 tipFooterLeft = ReadTipConfig.chapterTitle` |
| **正文里遗留的那一行标题** | 站点把标题渲染在正文容器内，解析层原样收下 |

本卡说的是第三个。

## 2. 代码路径（这是关键，也是最容易搞反的地方）

### 2.1 `ContentRule.title` **不删正文**

| 事实 | 依据 |
| --- | --- |
| `ContentRule.title` 的语义是「**有些网站只能在正文中获取标题**」 | `ContentRule.kt:15` |
| 它对正文页响应求值 | `BookContent.kt:59 setContent(body, baseUrl)`；`:176-199` |
| 取到后**只写** `bookChapter.title` / `imgUrl` / `titleMD5` | `BookContent.kt:195-197` |
| **`contentStr` 从头到尾没有被这段逻辑碰过** | `contentStr` 在 `:166` 拼接，`:176-199` 之间只被读；`:204` 判空、`:208` 存盘、`:210` 返回 |

**配了 `ruleContent.title` 既不会删掉正文里那一行，也不会把它标出来。**

### 2.2 唯一会删那一行的代码：展示期去重

`app/src/main/java/io/legado/app/help/book/ContentProcessor.kt:105-133`（注释 `//去除重复标题` 在 106 行）：

```kotlin
val name = Pattern.quote(book.name)
var title = chapter.title.escapeRegex().replace(spaceRegex, "\\\\s*")
var matcher = Pattern.compile("^(\\s|\\p{P}|${name})*${title}(\\s)*").matcher(mContent)
if (matcher.find()) { mContent = mContent.substring(matcher.end()); sameTitleRemoved = true }
else if (useReplace && book.getUseReplaceRule()) { /* 用 getDisplayTitle 再试一次 */ }
```

要点：

- **只改显示用的内存副本**，磁盘上的 `*.nb` 正文缓存不动（`ReadBook.kt:817 includeTitle = false`）；
- **默认开启**，按章节可关：缓存目录存在 `第00012-xxxx.nr` 即禁用该章（`ContentProcessor.kt:74-81`、`BookHelp.kt:475-512`），菜单位于 `ReadBookActivity.kt:637-651`；
- `sameTitleRemoved`（`ContentProcessor.kt:221`）**只服务菜单/toast**，`TextChapterLayout` 从不读它。

### 2.3 匹配很脆 —— 这才是「标题重复」的主因

`title` 经 `escapeRegex` 后仅把空格换成 `\s*`。于是：

| 正文首行 | 目录标题 | 是否命中 | 后果 |
| --- | --- | --- | --- |
| `第一章 初入仙门` | `第一章 初入仙门` | 命中 | 正常 |
| `　　第一章 初入仙门`（U+3000 缩进） | `第一章 初入仙门` | **Java 默认模式 `\s` 不匹配 U+3000** → 不命中 | 标题留一行 |
| `第102章 夜雨` | `第一百零二章 夜雨` | 不命中 | 标题留一行 |
| `第一章 初入仙门（免费）` | `第一章 初入仙门` | 标题后多后缀 → 不命中 | 标题留一行 |
| `【第一章】初入仙门` | `第一章 初入仙门` | 包裹符不在 `\p{P}` 白名单内 → 不命中 | 标题留一行 |

第一次不中时才用 `getDisplayTitle`（带标题净化规则）重试一次（`:117-129`）——这是用户「标题净化规则」能救回重复标题的原因。

**而通用层自己在正文行首加缩进**：`BookContent.kt:172-174`，书源内 `replaceRegex` 生效时，在线文本会被重新缩进成 `"　　$it"`（U+3000 ×2）。也就是说**通用层会亲手把上面那一行推进「不命中」的格子**。

### 2.4 另一条默认关闭的路径

`ContentProcessor.kt:134-137` → `ContentHelp.kt:28-33`：首段与 `chapter.title` 相同则丢弃。开关 `book.getReSegment()`（`Book.kt:488`）默认 `false`。

## 3. 规模（脱敏读数）

**全部读数由 `tools/book-source-audit/` 直接给出**，可 `--full` 重跑复现（命令见本节末尾）。
单份清单（S）与 `--merge-collections` 归并（M）两套口径并列：

| 层 | 工具里的判据 | S 全部（启用） | M 全部（启用） |
| --- | --- | --- | --- |
| **T** | 旗标 `has_title_rule` | **0**（0） | **36**（26） |
| **T¬** | 检查 `title_rule_no_dedup` —— T 且**没有**去标题正则 | 0（0） | **33**（24） |
| **N** | 检查 `title_selector_named` —— 选择器部分点名标题节点 | 11（9） | 11（9） |
| **Njs** | 检查 `title_selector_named_js_only` —— 只在 JS 片段里出现 | 134（83） | 136（93） |
| **RR** | 旗标 `title_dedup_evidence == replace_regex` | 160（139） | 161（144） |
| T ∪ N | 正向证据中「选择器可证实」的部分 | 11（9） | 47（35） |
| **T ∪ N ∪ Njs** | **最宽正向证据 —— 本卡采用的下界** | **145**（92） | **181**（126） |
| T ∪ N ∪ RR | 最宽并集（含「作者已承认、但已缓解」的） | 171（148） | 205（177） |
| T ∩ RR | 两个字段都写了的 | 0（0） | 3（2） |

> **口径警告**：`has_title_rule` 在单份清单里是 **0**，归并后是 **36**。原因是整个 zip 有 16 份书源合集
> （16155 条引用 → 6139 唯一 URL），`bookSource.json` 只是其中一份；另外 15 份里 60 条带 `title`，
> 归并去重后落在 36 个唯一 URL 上。**任何「全库多少」不声明口径就没有意义**——
> 这条已经被一次实际误判踩中（见 [`../语料归因.md`](../语料归因.md) 的「四、被推翻的判定」）。

**估计：约 180—350 个源，中心约 230。**

- **下界 181**（M 口径的 T ∪ N ∪ Njs）是**静态可证实**的部分：这 181 个源里有明确的、正向的
  证据说明「标题文本能从正文页取到」，而且其中 126 个是启用态。
- **右端 350** 给的是**静默层**——正文选择器选中一个包住 `h1` 的容器（`#content`、`.read-content`），
  选择器文本里既没有 `title` 也没有 `h1`，作者也什么都没写。这类**静态完全不可见**，
  所以 181 是下界而不是估计值。

### 与本节早先一版读数的差异（必须说明）

本节的第一版数字（T∪N = 134、RR = 152、T∪N∪RR = 284）来自一次性的分析脚本，
**不是工具输出的**。改用工具重跑后对不上，原因有三条，都已修进工具：

1. **JS 片段的切分位置错了**。原脚本按「第一个 `##` 之前」切选择器，
   但 `AnalyzeRule.kt:544-566` 是**先摘 JS 片段**再判前缀 —— `@js:…##…` 里 `##` 之前的整段
   其实是 JS。按 `##` 硬切会把 JS 误算成「选择器点名标题」（S 口径 96 → 实为 11）。
   已改用 `rule_source.split_segments()`，与真实求值顺序一致。
2. **去标题正则与 `ruleContent.title` 是互相独立的**。快照里绝大多数作者只用前者
   （`{{chapter.title}}` 插值），根本没写 `title` 字段。原脚本把两者绑在一个分支里，
   会把 160 条「有去重、无 title」误记成 `no_title_rule`。
3. 因此 RR 从 152 修正为 **161**，N 从 98 修正为 **11 + 136**。

**本卡现在只采信工具读数。** 上表每一行都能用下面的命令复现，且 `--label` 会让
两种口径分别落盘、互不覆盖。

### 误差来源（按影响排序）

1. **口径必须写死**：T 从 0 跳到 36，启用分母从 4000 跳到 4417；
2. 选择器命中「哪个子树」只有跑起来才知道，181 系统性偏低；
3. Njs 层 136 个只在 JS 片段出现，是**弱证据**（`title` 也可能是 `document.title`）；
4. T 层 36 个是「标题**可取到**」而不是「标题是**一行可见文字**」——也可能在 `title=` 属性里，这个方向上 36 偏**高**；
5. RR 层「已处理」不等于「一定处理掉」，`{{chapter.title}}` 是字面串匹配；
6. 图片/音频/文件类没有「正文行」概念（按 `bookSourceType==0` 过滤后 T ∪ N ∪ Njs = 173，变化不大）。

| 层 | 结论 |
| --- | --- |
| 请求层 | 无关 |

| 结论 | **需通用层改动**（候选），但先要满足 §7 退出条件 |

### ⚠️ 与本计划的一处冲突，必须由你裁决

`docs/book-source-audit/语料/` 里 D03、I01 两条样例的**预期是「保留标题」**：

- D03：`上一章 目录 下一章\n第三章 山雨\n乌云从西边压了过来。` → 预期保留 `第三章 山雨`
- I01：`第一章 初入仙门\n第一章 初入仙门\n山门外站着一名少年。` → 预期**删掉一行**（保留一行）

而本卡的现存缺陷是「标题行没被删掉」。**「删」与「不删」这两个方向如果定错，会把 D03/I01 改坏。**
本卡的立场是：**只在「正文首行 == 目录标题」时删，且删除只发生在展示副本**（沿用现有设计），
D03 的 `第三章 山雨` 与上一行的导航是两个独立现象，不冲突。
